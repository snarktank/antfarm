Completed story results:
- Hardened the vulnerable `/fetch` endpoint in `src/server.js` so it now requires a non-empty, strictly parsed URL instead of blindly fetching `req.query.url`.
- Added explicit outbound fetch policy controls: only `https:` URLs to the hostname allowlist (`example.com`, `www.example.com`) are permitted, credentials in URLs are rejected, and hostnames resolving to localhost, RFC1918, link-local, loopback, unique-local, and metadata-style internal IP space are blocked.
- Replaced automatic redirect following with manual redirect validation in `fetchAllowedUrl(...)`, so every hop is re-validated and redirect chains cannot bounce an allowed URL into an internal target.
- Added an outbound request timeout using `AbortController` and capped redirect depth to fail closed on hanging or abusive upstream behavior.
- Added a regression test in `test/web-security.test.js` that verifies direct localhost SSRF is rejected and that a redirect from an allowlisted host to a metadata IP is also rejected.
- Verified `npm run build` passes.
- Verified `npm test` passes.

Patterns:
- SSRF defenses should validate the fully parsed URL, not raw strings, and should enforce both protocol and destination allowlists.
- Treat DNS resolution as part of authorization: block requests when a hostname resolves to internal, loopback, or link-local IP space even if the hostname itself looks benign.
- Disable automatic redirect trust for server-side fetches; validate each redirect hop before issuing the next request.
- Add explicit outbound timeouts so security controls do not leave the process hanging on malicious or unreachable upstreams.
