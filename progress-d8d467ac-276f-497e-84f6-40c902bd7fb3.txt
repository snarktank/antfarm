Story fix-009: Add CSRF protections on state-changing endpoints

Completed:
- Added targeted CSRF enforcement in `src/server.js` for the state-changing `/run`, `/admin/delete-user`, and `/deserialize` POST routes.
- Implemented strict same-origin validation for cookie-authenticated requests by checking the request `Origin` header first and falling back to `Referer`, then rejecting missing or cross-site sources with `403 { error: 'CSRF validation failed' }`.
- Scoped the guard to requests that present the app `sid` cookie so existing non-cookie API flows are not broken while browser-backed session requests gain CSRF protection.
- Extended `test/web-security.test.js` with an end-to-end regression test that first obtains a live session cookie, then proves forged cross-site POSTs to `/run` and `/admin/delete-user` are blocked, same-origin requests still succeed, and cookie-backed POSTs without `Origin`/`Referer` are rejected.
- Verified the fix with `npm run build` and `npm test`.

Patterns / learnings:
- For cookie-backed state changes, SameSite helps but server-side same-origin validation closes the loop and should explicitly reject requests with missing provenance headers.
- A minimal CSRF fix can be applied route-by-route without disturbing unrelated authentication or input-validation logic.
- Regression tests should simulate a real browser flow by minting a live session cookie first; otherwise CSRF coverage can miss the exploitable path.
- Keeping CSRF checks conditional on the presence of the session cookie avoids unintentionally breaking non-browser clients that are not using cookie authentication.
