Completed story results:
- Replaced the vulnerable `eval`-based `/deserialize` implementation in `src/server.js` with `JSON.parse` so request payloads are handled strictly as JSON data instead of executable code.
- Added explicit schema validation for deserialized payloads and only accept plain objects with exactly two fields: a non-empty string `type` and a primitive-or-null `value`.
- Closed the endpoint on malformed JSON, non-string `payload` inputs, and schema-invalid objects by returning HTTP 400 with `Invalid payload`.
- Added a regression test in `test/web-security.test.js` that submits an `eval`-style code-execution payload, verifies it is rejected, and confirms no attacker-controlled file is written.
- Added a positive test case proving a schema-valid JSON payload is still accepted by `/deserialize`.
- Verified `npm run build` passes.
- Verified `npm test` passes.

Patterns:
- When an endpoint expects serialized data, parse it with a data-only parser such as `JSON.parse` and reject any format that would require code execution to interpret.
- Define a narrow schema for accepted payloads and reject extra fields, wrong types, arrays, and non-object values so the endpoint fails closed.
- Regression tests for insecure deserialization should include a payload that would have executed under `eval`, plus a safe payload that demonstrates the intended contract still works.
