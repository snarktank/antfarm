Story fix-010: Restrict CORS and apply baseline HTTP security headers

Completed:
- Replaced the wildcard CORS behavior in `src/server.js` with an explicit trusted-origin allowlist that permits only approved app origins plus local development origins, and only advertises the required `GET`/`POST` methods and expected request headers.
- Added centralized baseline response hardening in `src/server.js` with `Content-Security-Policy`, `X-Frame-Options: DENY`, and `X-Content-Type-Options: nosniff`, plus conditional `Strict-Transport-Security` on secure requests.
- Added strict OPTIONS preflight handling so trusted origins receive a `204` CORS response while untrusted origins are denied with `403` instead of inheriting permissive behavior.
- Extended `test/web-security.test.js` with an integration regression test that proves trusted origins receive the narrowed CORS policy and security headers, untrusted origins do not get CORS access, and hostile preflights are rejected.
- Verified the fix with `npm run build` and `npm test`.

Patterns / learnings:
- CORS should echo only known trusted origins; omitting `Access-Control-Allow-Origin` for everything else is safer than trying to sanitize arbitrary origins.
- Baseline browser hardening can be applied with a small shared middleware layer, which keeps header policy consistent across routes without broad refactors.
- HSTS should be emitted only for secure requests, while CSP, frame protections, and MIME sniffing protections should be applied universally.
- Regression tests for CORS should cover both simple requests and OPTIONS preflight behavior, because exploitable misconfigurations often hide in preflight handling.
